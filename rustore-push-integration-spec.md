## 1. Цель и ожидаемый результат

Добавить в библиотеку доставку Android-уведомлений через RuStore наряду с существующей доставкой через FCM. На iOS сохранить APNs.

Приложение должно получать токен выбранного провайдера через общий API, передавать его PHP-серверу и обрабатывать уведомления через существующие подписки. Для RuStore должны работать текст, изображение, кнопки, нажатие на уведомление и запуск приложения по нажатию после завершения процесса.

Это задание на реализацию. Предложенные ниже новые методы, поля, ошибки и настройки пока отсутствуют в библиотеке. Фрагменты показывают целевой контракт, а не готовую интеграцию.

### Обязательный объём

- Нативная интеграция RuStore в Android-части библиотеки.
- Возможность собирать библиотеку с поддержкой RuStore и без неё.
- Выбор одного активного Android-провайдера на сборку приложения.
- Сохранение существующего способа использования FCM.
- Единые события сообщений, нажатий и обновления учётных данных.
- Документация подключения, пример приложения и пример отправки из PHP.
- Автоматические проверки и проверка реальной доставки на устройствах.

### За пределами первой версии

- Автоматическое переключение между FCM и RuStore при временных ошибках.
- Одновременная отправка одного события через два провайдера одной установке.
- Добавление HMS, Xiaomi, OPPO, vivo и Meizu SDK.
- Топики, массовые рассылки и интерфейс управления кампаниями.
- Гарантированная доставка при Android Force stop.
- Полноценный фоновый JavaScript-обработчик и гарантированное хранение всех входящих сообщений.
- Перенос изменений в `capacitor-push-signal`.

В `AGENTS.md` репозитория отдельно оговорён перенос в Capacitor: он выполняется после готовности и проверки изменений и отдельного подтверждения владельца. В рамках этого задания изменяется React Native-библиотека.

## 3. Решение по выбору провайдера

Для первой версии выбрать **один активный Android-провайдер на сборку**:

- Если настройка отсутствует, активен `fcm` — существующее поведение.
- Для сборки RuStore явно настроен `rustore`.
- На iOS всегда используется `apns`.

Источник истины для Android — нативная конфигурация сборки, доступная до старта React Native. Она необходима для входящих сообщений и запуска процесса без открытого экрана.

Не определять провайдера по магазину установки, производителю телефона или одному наличию пакета RuStore. Не переключать его из-за временного сетевого сбоя.

JavaScript может явно указать ожидаемый провайдер при `initialize()`, но это проверка конфигурации, а не переключатель. При несовпадении с нативной настройкой возвращать понятную ошибку. Повторная инициализация с тем же провайдером должна быть безопасной.

## 4. Нативное подключение RuStore

Встраивать Kotlin/Java SDK непосредственно в библиотеку. Не добавлять вторую React Native-обёртку поверх существующего TurboModule.

### Проверенные внешние требования

На дату подготовки документа документация RuStore обозначает Kotlin/Java SDK `7.5.0` актуальным. Maven-репозиторий: `https://nexus-external.rustore.ru/repository/maven-rustore-exposed/`, артефакт: `ru.rustore.sdk:pushclient:7.5.0`.

SDK предусматривает раннюю инициализацию, в том числе через метаданные манифеста; ручной запуск выполняется из `Application.onCreate()` в главном процессе. Сервис получения наследуется от `RuStoreMessagingService`; обработчик должен завершаться за 20 секунд. Доступность проверяется через `checkPushAvailability()`: доставку обеспечивает приложение-дистрибьютор, поэтому отсутствие пакета RuStore само по себе недостаточно для вывода о недоступности. Android 13+ требует разрешения на показ. Package name и подпись сборки должны соответствовать push-проекту. SDK самостоятельно показывает заполненный `notification`; для собственного отображения использовать `data` без `notification`. Источник: [официальная инструкция Kotlin/Java](https://www.rustore.ru/help/sdk/push-notifications/kotlin-java/7-5-0).

Перед реализацией перепроверить требования выбранной версии SDK, зафиксировать её и не использовать динамические версии зависимостей.

## 5. Изменения внутренней архитектуры

Выделить минимальный внутренний контракт провайдера: его идентификатор, состояние готовности, получение токена и проверка доступности. Firebase-специфичные действия оставить в FCM-адаптере.

Рефакторинг ограничить необходимым для двух Android-провайдеров; не строить универсальную систему под все перечисленные в диагностике сервисы.

5. Отдельно учитывать готовность нативного адаптера, JavaScript-моста и JS-подписчиков.

## 6. Публичный API

### 6.1. Инициализация

Сохранить существующий тип `AndroidFirebaseConfig` и старые вызовы. Добавить новый тип:

```ts
export interface PushSignalConfig extends AndroidFirebaseConfig {
  /** Ожидаемый Android-провайдер; должен совпасть с нативной настройкой. */
  provider?: 'fcm' | 'rustore';
}

export function initialize(config?: PushSignalConfig): Promise<void>;
```

Поведение:

- `initialize()` использует нативную конфигурацию; при её отсутствии — FCM.
- Старые Firebase-поля продолжают поддерживаться.
- `initialize({ provider: 'rustore' })` проверяет готовность настроенного RuStore-пути.
- При выборе RuStore не требовать Firebase-полей.
- Явно переданные Firebase-поля в RuStore-режиме считать ошибкой конфигурации, чтобы не скрывать неверную интеграцию.
- При `provider: 'rustore'` без включённого SDK возвращать ошибку, не падать при загрузке класса.
- На iOS Android-настройки игнорировать, сохраняя существующее кроссплатформенное использование.

Пример целевого использования в приложении:

```ts
import {
  initialize,
  getCredentials,
  onCredentialsChanged,
} from 'react-native-push-signal';

// registerDevice — функция приложения, отправляющая данные в свой API.
// Обрабатывать её сетевые ошибки и повторять регистрацию при следующем запуске.
const unsubscribe = onCredentialsChanged(async (credentials) => {
  await registerDevice(credentials);
});

await initialize();
await registerDevice(await getCredentials());

// При освобождении владельца подписки: unsubscribe().
```

Пример намеренно не содержит запрос разрешения: приложение должно выполнить его в подходящем месте пользовательского сценария. Получение токена и разрешение на показ — разные состояния.

### 6.2. Credentials

Добавить отдельный тип фактически поддержанной доставки, не смешивая его с эвристической диагностикой других сервисов:

```ts
export type PushTransport = 'fcm' | 'rustore' | 'apns';

export interface PushCredentials {
  token: string;
  environment?: PushEnvironment;
  provider?: PushTransport;
}
```

Поле `provider` оставить необязательным в публичном типе для исходной совместимости с существующими объектами и mocks. В новой нативной реализации оно обязательно заполняется при каждом успешном ответе: Android — выбранным провайдером, iOS — `apns`.

Если JS-код новой версии работает со старым ответом без поля provider, нормализовать его как прежний FCM на Android или APNs на iOS. Не выдавать RuStore-токен как FCM. Сохранить APNs `environment` без изменений.

Обновить native codegen-тип, преобразования Kotlin/Objective-C, нормализатор JS, экспорты и mocks. Не добавлять `android` как enum-значение вместо существующего `android_os`: в исходниках отмечен конфликт с NDK-макросом.

### 6.3. Обновление токена

Добавить:

```ts
export function onCredentialsChanged(
  listener: (credentials: PushCredentials) => void | Promise<void>
): () => void;
```

Контракт:

- Источники: новый FCM-токен, новый RuStore-токен и callback регистрации APNs.
- Повтор одинаковых `provider + token + environment` не порождает повторное событие в рамках текущего состояния.
- При отсутствии JS сохранить последние credentials для последующей выдачи; не хранить неограниченную историю токенов.
- При появлении первого подписчика выдать последнее недоставленное изменение один раз.
- `getCredentials()` возвращает актуальное значение независимо от подписки.
- Подписка возвращает рабочую функцию отмены, несколько подписчиков поддерживаются.
- Ошибка одного слушателя не мешает остальным.
- Секретные значения не выводятся в логи целиком.

Если используется постоянный кеш, защитить его от восстановления устаревшего токена из Android backup. Источник актуального токена после запуска — SDK. Событие не заменяет повторную регистрацию credentials на сервере при запуске приложения и входе в аккаунт.

### 6.4. Диагностика и ошибки

Добавить `rustore` в `PushProvider`. Сохранить значения существующих полей диагностики и их совместимость. Добавить необязательные поля:

- `activeProvider`: выбранный реальный транспорт.
- `pushAvailable`: результат проверки активного адаптера, если он уже известен.
- `availabilityReason`: понятная причина недоступности.

Не переопределять незаметно старое поле `provider`, которое использовалось для рекомендации альтернативы. Описать отличие в README. `providerInstalled` и `pushAvailable` не считать синонимами.

Предлагаемые стабильные ошибки библиотеки:

- `E_RUSTORE_NOT_INCLUDED` — сборка не содержит адаптер.
- `E_RUSTORE_CONFIG` — нет корректной нативной конфигурации.
- `E_PROVIDER_CONFIG_MISMATCH` — JS ожидает другой провайдер.
- `E_RUSTORE_UNAVAILABLE` — доставка недоступна по результату SDK.
- `E_RUSTORE_INIT` — ошибка запуска SDK.
- `E_RUSTORE_TOKEN` — ошибка получения токена.

Сохранять исходную причину SDK, если она доступна, и не угадывать точную причину вроде несовпадения подписи по любому общему сбою. Не обогащать RuStore-ошибку советом настроить Google Play Services.

Обновить dev-panel: отображать активный транспорт, состояние, события токена и ошибки. Web-заглушка должна экспортировать новый метод подписки как безопасный no-op; существующие неподдерживаемые операции остаются неподдерживаемыми.

## 7. Формат сообщений и показ уведомлений

### 7.1. Основной формат RuStore

Для уведомлений, отображаемых библиотекой, использовать только `message.data`, без `message.notification` и `message.android.notification`.

Предлагаемый payload:

```json
{
  "message": {
    "token": "DEVICE_PUSH_TOKEN",
    "data": {
      "push_id": "order-123-ready-1",
      "title": "Заказ готов",
      "body": "Можно забирать",
      "image": "https://example.com/order.jpg",
      "buttons": "[{\"id\":\"open_order\",\"title\":\"Открыть заказ\",\"url\":\"myapp://orders/123\"}]",
      "order_id": "123"
    },
    "android": {
      "ttl": "3600s"
    }
  }
}
```

Транспорт RuStore принимает строковые значения `data`; максимальное сообщение — 4096 байт. Отправка: `POST https://vkpns.rustore.ru/v1/projects/{project_id}/messages:send`, авторизация — `Authorization: Bearer {service_token}`. Эти параметры и значения ошибок перепроверять по [официальному API отправки](https://www.rustore.ru/help/sdk/push-notifications/send-push-notifications).

`push_id` — предлагаемый идентификатор прикладного события для этой библиотеки, а не специальное поле RuStore. Названия `image` и `buttons` сверить с существующими константами библиотеки и сохранить текущий формат.

### 7.2. Нормализация

- `PushMessage.id`: непустой `data.push_id`, иначе ID сообщения SDK.
- Заголовок и текст: строки `data.title` и `data.body` для основного формата.
- Все исходные строковые поля оставить в `PushMessage.data`.
- Изображение и кнопки разобрать существующими helper-функциями после проверки совместимости.
- Ошибочный JSON кнопок не должен ломать текст уведомления.
- Пустое техническое сообщение без отображаемого содержимого не создаёт пустое уведомление.
- Не открывать URL автоматически при получении. Действия выполнять только после пользовательского нажатия и проверки маршрута приложением.

### 7.3. Кто показывает уведомление

Для RuStore data-сообщений библиотека показывает отображаемое уведомление и в открытом приложении, и в фоне. Это отдельная политика от существующего FCM-пути.

Обычное текстовое RuStore data-сообщение без кнопок обязано отображаться в фоне. Текущее условие, ориентированное на наличие кнопок, нельзя переиспользовать без изменений.

Если пришло сообщение с заполненным `notification`, считать его режимом показа SDK. Библиотека не создаёт второй системный показ. Для первой версии допускается ограничить гарантии собственных кнопок и обработки нажатия документированным data-форматом; явно описать это ограничение и проверить отсутствие дублей у notification-сообщений.

Создать или использовать существующий notification channel. Отказ в разрешении или отключение канала не должен приводить к падению. Если изображение недоступно, показать текст; загрузка не должна блокировать получение сообщения или зависеть от живого JS. Не рассчитывать, что произвольная фоновая задача продолжит работать после уничтожения процесса: выбрать подходящий Android-механизм либо сначала показывать текст и безопасно обновлять изображение.

### 7.4. Нажатия, кнопки и холодный старт

- Для собственных уведомлений использовать общий формат внутренних Intent extras с пространством имён библиотеки.
- Сохранить распознавание существующих FCM extras ради обратной совместимости.
- Обработать нажатие при открытом приложении, в фоне и после завершения процесса.
- Сохранить событие до подключения JS-подписчика, чтобы стартовый Intent не потерялся.
- Для кнопки заполнить `action` и вернуть соответствующий `PushButton` через `onNotificationAction`.
- `PendingIntent` разных сообщений и кнопок не должны перезаписывать друг друга.
- Проверить необходимые flags и явный Intent приложения.
- Нажатие не должно одновременно порождать два одинаковых события из разных Android callbacks.

### 7.5. Повторы и ограничения

Дедупликацию выполнять по фактическому provider и стабильному ID сообщения в ограниченном кеше. Сообщения без ID не объединять все в одну запись. Повтор одного push не должен создавать две карточки и два одинаковых JS-события в пределах заявленного окна дедупликации.

Не обещать exactly-once доставку. Гарантии кеша, его размер, TTL и поведение после перезапуска описать в README. Для критических действий приложение использует серверную идемпотентность по `push_id`.

Очередь событий до старта JS и долговременный inbox — разные механизмы. Первая обязательна; второй в задачу не входит. Уничтожение процесса может уничтожить недоставленное событие `onMessage`, но нажатие на уже показанное уведомление должно восстановить его payload из Intent.

## 8. Требования к PHP-серверу

В репозитории библиотеки подготовить рабочий пример отправки и описание серверного контракта. Изменение боевого PHP-проекта — отдельная работа, поскольку его исходники не предоставлены.

### 8.1. Регистрация установки

Пример тела авторизованного запроса приложения:

```json
{
  "installation_id": "APP_GENERATED_INSTALLATION_ID",
  "provider": "rustore",
  "token": "DEVICE_PUSH_TOKEN",
  "platform": "android_os",
  "app_version": "1.2.3"
}
```

Предлагаемые поля записи: `id`, `user_id`, `installation_id`, `application_id`, `provider`, `token`, `environment`, `updated_at`, `active`. Имена можно согласовать со схемой сервера.

Правила:

- Пользователя определять по авторизации, а не доверять переданному `user_id`.
- Поддерживать несколько установок у одного пользователя.
- Повтор регистрации делать идемпотентным.
- В одной установке хранить один активный транспорт в рамках выбранной модели.
- При обновлении токена заменять старую привязку атомарно.
- При смене аккаунта или выходе отвязывать установку от прежнего пользователя.
- После обновления приложения со сменой провайдера деактивировать старый маршрут доставки.
- `installation_id` генерируется приложением; не использовать аппаратные идентификаторы.
- Проект RuStore и сервисный ключ сервер выбирает из своей конфигурации, а не принимает произвольными от клиента.

### 8.2. Отправитель

Подготовить пример `examples/php/send-rustore-push.php` либо разместить его в принятом для проекта каталоге примеров. Указать нужную версию PHP и расширение cURL.

Пример должен:

1. Читать ID проекта и сервисный токен из переменных окружения.
2. Принимать токен получателя и прикладные данные через явные параметры, не из открытого HTTP endpoint без авторизации.
3. Формировать data-payload из раздела 7, сериализуя кнопки в JSON-строку.
4. Проверять ошибки JSON и размер сформированного сообщения в байтах.
5. Использовать HTTPS, тайм-аут соединения и общий тайм-аут запроса.
6. Различать сетевую ошибку, HTTP-ошибку и успешное принятие запроса.
7. Разбирать структурированную ошибку сервиса.
8. Маскировать токены в диагностике.

Сервисный ключ запрещено помещать в JS bundle, APK, настройки приложения или репозиторий. Успешный HTTP-ответ означает принятие запроса, а не доставку на устройство и не прочтение.

Для боевого отправителя предусмотреть очередь: временные ошибки повторять с ограничением попыток и увеличением задержки; ошибки авторизации и формата не повторять бесконечно. Деактивацию токена выполнять только по документированному ответу об его недействительности, не по любому HTTP 4xx/5xx. При неопределённом результате повтор может дать дубль, поэтому повторные попытки сохраняют тот же `push_id`.

Маршрутизатор PHP отправляет FCM-токены в FCM, RuStore-токены в RuStore, APNs-токены в APNs. Старым Android-записям без provider можно назначить FCM только после проверки, что исторически они действительно были FCM-токенами.

## 10. Проверки

### 10.1. Автоматические тесты

Расширить существующие тесты и добавить проверки нативной логики там, где нужен Android-контекст. Тестировать поведение, а не только наличие новых методов.

Обязательные сценарии:

1. Старый Firebase-конфиг принимается без изменений.
2. Отсутствие provider сохраняет прежний FCM-путь, если нет нативной настройки.
3. RuStore-путь не вызывает проверку GMS и не требует Firebase credentials.
4. Несовпадение JS-ожидания и нативного провайдера даёт структурированную ошибку.
5. Выбор RuStore в сборке без адаптера не вызывает `ClassNotFoundException`.
6. Нормализация credentials сохраняет environment и правильно добавляет provider.
7. Событие обновления токена до подписки не теряется; повтор того же токена подавляется.
8. Отписка и повторное подключение ReactContext не создают двойные события.
9. Текстовое data-сообщение RuStore отображается в фоне без кнопок.
10. Notification-сообщение RuStore не рисуется библиотекой повторно.
11. Неверный JSON кнопок и ошибка изображения не ломают текстовую карточку.
12. Повтор push с тем же ID не дублирует обработку; разные provider и сообщения без ID не конфликтуют.
13. Стартовый Intent и последующий `onNewIntent` не дублируют одно нажатие.
14. Ошибки RuStore сохраняют свою причину и не превращаются в рекомендации настроить GMS.
15. Web-экспорты и существующий iOS API остаются совместимыми.

### 10.2. Проверки сборки

- Запустить `yarn typecheck`, `yarn lint`, `yarn test` и сборку библиотеки через существующий `yarn prepare`.
- Собрать Android example без RuStore и с RuStore, в debug и release.
- Проверить release с минификацией и содержимое итогового манифеста.
- Проверить, что сборка без RuStore действительно не разрешает его зависимости.
- Проверить TurboModule codegen на Android и iOS.
- Собрать iOS example с существующей интеграцией APNs.
- Проверить npm-артефакт, включение дополнительных source set и отсутствие секретов.

Если команда или окружение недоступны, явно отметить это в отчёте. Успешный TypeScript-тест не считается проверкой Android-сборки или доставки.

### 10.3. Проверка реальной доставки

На каждую проверку записать устройство, версию ОС, версию SDK, сборку приложения, активный провайдер, отправленный `push_id` и фактический результат. Не сохранять открытые ключи и токены в отчёт.

Минимальные конфигурации:

- Android с GMS, выбран FCM: регрессия существующего поведения.
- Android с GMS и доступным RuStore-транспортом, выбран RuStore: используется именно RuStore.
- Android без GMS с доступным RuStore-транспортом: получение токена и пуша.
- Android без доступного дистрибьютора: понятная ошибка без падения.
- Android 13+ с разрешением и с отказом; отдельно отключённый канал уведомлений.
- Самая старая поддерживаемая ОС на устройстве или эмуляторе, насколько доступна инфраструктура SDK.
- iOS: токен APNs, получение, нажатие, изображение и кнопки по существующей схеме.

Для RuStore проверить:

- Приложение открыто.
- Приложение в фоне.
- Процесс завершён системой, но приложение не находится в состоянии Force stop.
- Нажатие на уведомление запускает приложение с правильным payload.
- Нажатие каждой кнопки возвращает правильный action и сообщение.
- Временное отсутствие сети и восстановление соединения.
- Истечение TTL: устаревшее событие не используется как актуальная истина без сверки с сервером.
- Ограничения фоновой работы дистрибьютора: корректная диагностика, без обещания мгновенной доставки.
- Debug/release с правильной и неверной настройкой проекта/подписи.
- Переустановка и очистка данных: сервер получает актуальные credentials.
- Вход, выход и смена аккаунта: уведомления не уходят прежнему пользователю этой установки.

Force stop проверить отдельно и задокументировать наблюдаемое поведение. Не использовать его как эквивалент обычного завершения процесса.

## 12. Критерии приёмки

- [ ] Сборка RuStore получает токен без зависимости от наличия GMS.

- [ ] Текст без кнопок отображается в фоне.

- [ ] На iOS сохранены APNs environment и прежнее поведение уведомлений.
- [ ] Ошибки конфигурации и недоступность RuStore диагностируются без подсказок о Firebase.
